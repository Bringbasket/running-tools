# Running Tools 界面设计规范

本文档是 Running Tools 所有前端页面的设计与验收依据。新增页面、重构页面和代码审查都必须遵守；若业务确实需要例外，应在对应模块文档中说明原因，而不是在页面内自行创造另一套视觉语言。

## 1. 产品定位

Running Tools 是需要长期、重复操作的管理工具，不是营销落地页。界面应当安静、紧凑、清楚，让用户快速扫描状态并完成操作。

设计关键词：**克制、可靠、高密度、层级明确、操作可预期**。

以下做法禁止作为默认设计：

- 为了填满页面堆放没有决策价值的指标卡。
- 在中文标题上方重复放置 `MAIL SYSTEM`、`WORKSPACE` 等英文眉题。
- 使用超大标题、渐变背景、装饰光斑或营销式说明文案。
- 页面区块全部做成悬浮卡片，或在卡片中继续嵌套卡片。
- 所有状态都使用品牌色；成功、警告、错误和普通信息必须有语义区别。
- 用大段说明文字解释界面如何操作。控制本身应当足够清楚。
- 同一操作同时出现在标题栏、工具栏和表格行中，造成重复入口。

## 2. 页面标准骨架

业务页面统一由以下区域按需组成：

1. 页面标题栏：左侧为中文标题和一句业务说明，右侧只放页面级主要操作。
2. 状态摘要：仅展示会影响当前决策的 2 至 4 项信息，优先使用紧凑横条，不默认使用独立卡片。
3. 视图切换：同一业务内的子功能使用标签页或分段控件，不拆成无关的一级菜单。
4. 工具栏：搜索、筛选、每页条数和批量操作在同一水平区域内组织。
5. 主数据区：列表优先使用表格；移动端可改为结构化列表，但信息顺序必须一致。
6. 分页栏：展示当前范围、总数、每页条数和前后翻页，不只提供两个无上下文按钮。

一个页面只允许一个视觉主区域。设置表单可以分节，但分节使用标题、分隔线和留白，不使用层层套卡。

模块级账号、租户或工作空间会改变多个子页面的数据上下文，必须放入所属模块的“账号管理”子菜单和
独立页面。平台顶栏只保留全局操作，不放账号切换器或账号创建浮层；短创建任务在账号管理页使用标准
弹窗完成，创建成功后明确标识当前账号。

## 3. 尺寸和间距

- 页面内容宽度由平台外壳统一控制，业务页面不得自行使用固定大宽度。
- 所有一级业务页面必须直接使用平台 `.page` 容器。业务页禁止覆盖 `.page` 的 `width`、
  `max-width`、水平 `margin`，也不得通过负外边距改变页面边界；需要限制宽度的仅限弹窗、
  抽屉、表单字段和正文阅读区等内部组件。
- 同一视口下切换邮箱管理、收件箱、API 调试、Session 管理和工具箱页面时，标题栏、主区域
  左右边界必须完全一致。页面内容多少不得改变外层容器宽度。
- 页面区块间距使用 `24px`；相关控件组间距使用 `12px`；紧密元素使用 `6px` 或 `8px`。
- 页面标题建议 `20px` 至 `24px`，面板标题 `14px` 至 `16px`，正文 `13px` 至 `14px`，辅助信息不小于 `11px`。
- 字号不得随视口宽度缩放，字间距保持 `0`。
- 表格行高建议 `44px` 至 `56px`；操作频繁的后台页面不使用大面积空白行。
- 卡片和弹窗圆角最大 `8px`；按钮、输入框建议 `6px`。
- 图标按钮至少 `32px × 32px`，常规按钮高度建议 `34px` 至 `38px`。

所有固定格式控件都必须有稳定尺寸。加载图标、状态文本、计数变化不能让按钮、工具栏或表格列跳动。

### 布局稳定性

- 平台必须为纵向滚动条预留稳定空间；展开面板、打开提示、切换标签页或数据从空态变为有内容时，
  页面不得因为滚动条出现或消失而发生水平位移。
- 同一按钮的空闲、加载、成功和失败状态必须保持相同外框宽高。加载图标应替换原图标，不能在
  原内容旁临时增加图标导致按钮或相邻控件移动。
- 表单标签与输入控件、同一操作行的按钮必须使用明确的网格轨道或清除字段默认外边距，禁止依靠
  文本高度或 `align-items: end` 偶然对齐。输入框和相邻按钮底线误差不得超过 `1px`。
- 异步加载区域应设置与最终内容匹配的最小高度；表头、工具栏、分页栏和弹窗操作区不得随加载态
  出现或消失。业务所需的展开和收起可以改变垂直高度，但不得带来横向抖动。
- 侧栏模块和子菜单使用统一的可用宽度、行高、图标列和文字起始线。选中背景必须覆盖完整的子菜单
  点击区，不能根据菜单数量或文字长度改变宽度。

## 4. 色彩和层级

- 品牌色只用于主操作、当前选中项和少量关键数据。
- 普通容器依靠背景、边框和留白建立层级，不依赖大面积品牌色。
- 成功使用绿色，警告使用琥珀色，错误使用红色，处理中使用中性色或品牌色。
- 浅色和深色主题都必须保证正文、辅助文字、边框和禁用状态有可辨识的对比度。
- 阴影只用于弹窗、下拉菜单和确实浮于页面之上的控件；普通页面区块不使用阴影。

## 5. 控件选择

- 明确命令使用“图标 + 文字”按钮；工具类操作优先图标按钮并提供 `title` 或 Tooltip。
- 布尔设置使用开关或复选框，不使用两个文字按钮模拟开关。
- 少量互斥模式使用分段控件，多个视图使用标签页，多个选项使用下拉菜单。
- 数值使用数字输入框、步进器或滑块；颜色使用色块；日期使用日期控件。
- 危险操作不能与主操作使用相同样式，执行前必须明确目标和后果。
- 操作提交后只显示真实结果；页面初次打开时不显示“请求已提交”等历史占位消息。

## 6. 数据表格和分页

- 列顺序按“身份信息 → 业务信息 → 状态 → 时间 → 操作”组织。
- 主要标识可以使用两行结构，第一行是名称或地址，第二行是辅助信息；不把三四种信息挤成一串。
- 文本过长时单行截断，并通过详情、Tooltip 或展开方式查看完整内容。
- 行操作保持在最右侧，低频操作收进菜单；熟悉图标已有明确含义时不重复放文字按钮。
- 空状态说明为什么为空，并只提供一个最相关的下一步操作。
- 加载时保持表头和整体尺寸稳定；失败状态不得伪装成空数据。
- 所有超过一屏的数据列表必须提供每页条数。默认 `10` 条，常用选项为 `10 / 20 / 50 / 100`。
- 分页必须显示“第几页 / 共几页”或当前记录范围及总数；搜索、筛选、每页条数变化后回到第一页。
- 批量选择只作用于当前已加载数据，界面必须准确显示已选数量。

## 7. 表单、反馈和状态

- 标签始终可见，不只依赖输入框占位符表达字段含义。
- 帮助文字只解释格式、限制或风险，不复述字段名称。
- 校验错误靠近字段显示；服务端错误在对应操作区显示，不使用无上下文的全局红条。
- 按钮加载状态只覆盖正在执行的操作，不能让无关按钮一起转圈。
- 成功提示简短且可自动消失；需要用户处理的失败信息必须持续显示。
- 后台任务应展示当前状态、最近执行时间、下次执行时间和最后错误，不用“可能正在运行”一类模糊文案。
- 全局短反馈统一调用 `showToast` 并由 `ToastHost` 呈现；成功信息自动消失，需要处理的错误仍应在
  对应操作区持续显示。页面不得自行实现另一套右上角提示。
- 加载、空数据和失败状态优先使用公共 `AsyncState`；状态文案和图标必须与真实请求阶段一致，
  不能在请求开始前显示“已提交”或“成功”。

## 8. 弹窗和抽屉

- 简短创建、编辑和确认使用弹窗；需要浏览大量内容或连续操作时使用独立页面或侧边抽屉。
- 弹窗标题直接描述任务，例如“编辑邮箱信息”，不添加英文眉题。
- 操作区固定在底部，取消在左、主要操作在右；关闭图标位于右上角。
- 弹窗最大高度不得超过视口，正文区域独立滚动，标题和操作按钮保持可见。
- 邮件、日志等长内容使用宽弹窗或抽屉，正文与元数据之间必须有清晰分隔。
- 标准弹窗必须复用 `AppDialog`，保留 Esc 关闭、Tab 焦点锁定、打开后首控件聚焦和关闭后焦点恢复。
  危险删除应要求输入完整目标名称确认；业务页面不得重复手写遮罩层和焦点逻辑。

## 9. 响应式和无障碍

- 必须验收 `1440×900`、`1024×768`、`390×844` 和最窄 `320px`。
- 页面不得出现非预期横向滚动；表格无法压缩时应切换为移动列表或提供明确的局部横向滚动容器。
- 文字不能覆盖按钮、状态或相邻内容，最长邮箱地址和错误信息必须能够换行或截断。
- 所有交互元素可通过键盘访问，并保留清楚的焦点样式。
- 图标按钮必须有可访问名称；状态不能只通过颜色表达。
- 动画只用于状态过渡和数值变化，并遵守 `prefers-reduced-motion`。
- 在上述视口中切换一级页面、展开折叠区、切换加载态各执行至少一次；使用截图或测量确认页面主区
  左右边界不变，侧栏选中项不变宽，表单输入框与操作按钮保持同一基线。

## 10. 页面交付检查

提交任何前端页面前必须完成：

- 检查是否遵循标准页面骨架，是否存在重复标题、重复操作或无用卡片。
- 检查加载、空数据、错误、禁用、成功和长文本状态。
- 检查浅色、深色主题和上述四种视口尺寸。
- 检查浏览器控制台无错误，页面无非预期横向溢出。
- 检查页面切换、数据加载、提示出现、折叠展开前后的主区域宽度；任一状态变化造成水平位移均不得交付。
- 运行 `npm run typecheck`、`npm run test:run` 和 `npm run build`。
- 数据列表新增或修改分页时，增加搜索、筛选、末页和每页条数回归测试。

## 11. 现有页面整改顺序

后续界面优化按以下优先级推进：

1. 高频核心流程：邮箱管理、收件箱、Session 管理。
2. 后台任务：自动刷新、自动创建和批量队列。
3. 工具页面：API 调试、保本测算。
4. 平台外壳：侧栏、顶栏、更新提示和登录弹窗。

整改时先改善信息架构和操作路径，再调整颜色和装饰。仅更换配色或增加卡片不算完成 UI 优化。
